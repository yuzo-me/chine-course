# Правила проекта для Claude Code

Ты — основной разработчик проекта. Читай этот файл полностью перед каждой задачей.

## 1. О проекте

Сайт-тренажёр слов и иероглифов HSK 1 (программа HSK 3.0) для учеников курса китайского.
Прототип к **пятнице 13.11.2026**. Полное описание: `docs/01-ТЗ-прототипа.md`. Архитектура: `docs/10-архитектура.md`.

## 2. Владелец не программист

- Владелец **не читает код**. Он проверяет поведение по чек-листу.
- Все сообщения и отчёты для владельца — **на русском, простыми словами**, без жаргона. Если термин неизбежен — поясни в скобках.
- Если нужно, чтобы владелец что-то сделал (установил, нажал, создал аккаунт) — дай **пошаговую инструкцию с точными командами**.
- Если задача неоднозначна или требует решения, которого нет в карточке задачи или в `docs/06-журнал-решений.md` — **остановись и задай вопрос**. Не принимай продуктовые решения сам.

## 3. Жёсткие ограничения продукта

1. **На сайте нет ИИ.** Никаких вызовов LLM, нейросетевых API, распознавания речи/рукописи нейросетями во время работы сайта. Вся проверка ответов — правилами и алгоритмами.
2. **Нет сервера и нет аккаунтов.** Статический сайт. Прогресс — в браузере (IndexedDB). Никаких личных данных пользователей не собирать.
3. **Нет аудирования и говорения** (это делает учитель). Звук есть только как озвучка отдельных слов, заранее сгенерированные файлы.
4. **Только упрощённые иероглифы**, интерфейс на русском.
5. **Работает офлайн** после первого открытия (PWA).

## 4. Стек (зафиксирован, не менять без вопроса)

| Часть | Технология |
|---|---|
| Сайт | React + TypeScript + Vite, папка `web/` |
| Хранилище | IndexedDB через Dexie |
| Офлайн | vite-plugin-pwa |
| Повторение | ts-fsrs |
| Пиньинь | pinyin-pro (и собственная нормализация ввода) |
| Письмо | hanzi-writer + данные hanzi-writer-data (только нужные знаки, локально) |
| Тесты | Vitest (логика), Playwright (сценарии; chromium + webkit) |
| Импорт данных | Python 3 + pdfplumber, папка `content/scripts/` |
| Хостинг | Cloudflare Pages (автодеплой из ветки `main`) |

Новую зависимость добавляй только если она необходима; в отчёте укажи: что, зачем, лицензия.

## 5. Структура репозитория

```
content/
  sources/        # скачанные первоисточники (PDF не коммитить, см. .gitignore)
  scripts/        # импорт и валидаторы (Python)
  data/           # итоговые JSON-данные курса — ЕДИНСТВЕННЫЙ источник контента
  audio/          # mp3 озвучки слов
  review/         # файлы для проверки учителем и его правки
web/
  src/
    app/          # маршруты, навигация, оболочка
    features/     # cards, exercises, dictionary, writing, progress, demo
    domain/       # чистая логика: pinyin, scheduling, scoring (без React)
    data/         # загрузка контента, Dexie
    ui/           # компоненты дизайн-системы и токены
  tests/e2e/      # Playwright
reports/          # отчёты по задачам
```

## 6. Правила работы над задачей

1. Задача описана в `tasks/T-XX-*.md`. Делай **только то, что в ней**. Лишнее — не делать, а предложить в отчёте.
2. Перед началом: `git checkout main && git pull`, затем ветка `task/T-XX`.
3. Работай маленькими шагами; после каждого рабочего шага — коммит с понятным сообщением на русском или английском.
4. **Тесты обязательны.** Логика в `domain/` — юнит-тесты. Каждый пользовательский сценарий из критериев приёмки — e2e-тест, если это возможно.
5. **Контент не хардкодить в коде.** Слова, переводы, пиньинь — только из `content/data/`. Никогда не исправляй контент вручную в коде.
6. Никаких секретов (ключей API) в репозитории. Ключи — только в `.env.local` (он в `.gitignore`).
7. Перед сдачей задачи выполни все команды:
   ```
   cd web && npm run lint && npm run typecheck && npm test && npm run build
   cd content && python3 scripts/validate.py   # когда валидатор уже существует
   ```
   Всё должно пройти без ошибок.
8. Напиши отчёт `reports/T-XX-отчёт.md` по шаблону ниже, закоммить, `git push -u origin task/T-XX`.
9. **Не сливай ветку в `main` сам.** Слияние — только после ревью Codex и приёма владельцем, по команде «Слей задачу T-XX».

## 7. Шаблон отчёта по задаче

```
# Отчёт T-XX
## Что сделано (простыми словами)
## Как проверить владельцу (шаги «нажать → увидеть»)
## Результаты команд (lint / typecheck / test / build / validate) — пройдено/нет
## Что не сделано или сделано иначе, и почему
## Новые зависимости (название, зачем, лицензия)
## Риски и слабые места этой реализации
## Вопросы к владельцу
```

## 8. Качество кода

- TypeScript strict, без `any` без причины.
- Логика отдельно от интерфейса (`domain/` не импортирует React).
- Доступность: кнопки с подписями, фокус с клавиатуры, результат не только цветом, минимальная зона нажатия 48×48.
- Китайский текст размечать `lang="zh-CN"`, пиньинь `lang="zh-Latn-pinyin"`. Шрифты: системные, стек с PingFang SC / Noto Sans SC / Microsoft YaHei, чтобы не подставлялись японские формы.
- Цвета и размеры — только из токенов (`web/src/ui/tokens`), значения из `docs/source/ТЗ-дизайн.md` §3–4.

## 9. Когда остановиться и спросить

- Задача требует изменить стек, структуру данных или выйти за рамки карточки.
- Данные источника не сходятся с контрольными числами (300 слов / 246 знаков / 100 знаков письма).
- Нужно платное действие, аккаунт или ключ.
- Тест не удаётся сделать зелёным за разумное время — не удаляй и не ослабляй тест, а опиши проблему.
